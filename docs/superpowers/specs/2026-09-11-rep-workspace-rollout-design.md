# Rep workspace rollout — design

**Date:** 2026-09-11 · **Owner:** Parker Marshall · **Status:** approved in session (home desktop)

## The problem

Black Box Safety has designed rep-facing AI infrastructure five times (bbs-ops/bbs-website,
bbs-sales, bbs-sales-vault, ca-quote-hub, bbs-rfq-automation) and deployed none of it to the
people it was built for. Rep machines run Claude Code in the Desktop app with hand-copied,
drifted skills that trace back to a OneDrive folder from June 2026. The managed-settings
design (2026-09-02) was finished and never pushed. The bbs-ops acceptance test was never
recorded. Two different `ca-rfq-intake` skills exist and collide silently.

The bottleneck is not design quality — it is that every rollout stalled at the deployment
step, and nothing enforces consistency once a machine is set up. Parker is the only
technical person (self-taught), so the system must be manageable by one busy non-engineer:
central control, no per-machine state, boring failure modes.

Meanwhile the sales team is trained, willing, and seeing ROI. They already: save inbound
RFQs into folders, point a Claude Code session (Desktop app) at the folder, and run skills.
The new SharePoint home base is being established at
`Black Box Safety - MASTER/Customers/State of CA Agencies/` (OneDrive-synced to each PC).

## The decision

**Marketplace-first thin client.** A rep machine has exactly four things, none hand-configured:

1. **Org managed settings** pushed from the Claude admin console (Team/Enterprise) —
   plugins, conservative permissions, company memory (`claudeMd`), announcements.
   Source of truth: `plugins/bbs-foundations/docs/bbs-managed-settings.json` in this repo.
   Local edits are overwritten on refresh; drift becomes structurally impossible.
2. **The marketplace plugins** (`bbs-foundations`, `bbs-sales`, `bbs-website` advisory,
   pinned externals) — ride in via managed settings, auto-update through git.
3. **The OneDrive-synced SharePoint folder** as the working home base, opened through a
   versioned `bbs-rep.code-workspace`, with a `CLAUDE.md` at the folder root generated by
   `bbs-claude-md-forge`.
4. **claude.ai connectors** assigned per role (BC read-only + M365 + Grainger for everyone;
   admin connectors stay with Parker/Griffin) — managed in claude.ai Settings, per the
   matrix in `MANAGED-SETTINGS.md`.

**Surface: VS Code standard, Desktop app unchanged.** Reps already run Claude Code inside
the Desktop app; that keeps working untouched and is the documented escape hatch. VS Code
is the encouraged standard because quote work is multi-document work (worksheet + attachments
+ precedent side by side, file tree visible next to Claude). Same Claude Code underneath —
same skills, sessions, connectors — so adopting VS Code is a window change, not a retraining.
The rep pitch, verbatim: *"Everything you do today keeps working. VS Code shows you what
Claude is reading."*

### Alternatives rejected

- **claude.ai web only** — no local folder access; fails the folder workflow.
- **Desktop app as the standard** — already works, but no file tree / side-by-side documents;
  kept as the fallback rather than the destination.
- **Power Platform rep app (bbs-rfq-automation)** — live parallel build targeting a Dataverse
  model-driven app. Formally **parked** as a rep destination: it has been blocked for weeks on
  enterprise-IT portal work only Parker can do, which is exactly the manageability failure
  this design avoids. Its ruled invariants (humans send quotes; sell = Grainger cost
  untransformed; no default-account fallback; nothing silently dropped) are already doctrine
  and are retained.
- **Supabase rep_cockpit (ca-quote-hub) as the home base** — parked. Folder-based tracking via
  `ca-rfq-intake` + `quote-log.md` covers v1; revisit the database pipeline only if folder
  tracking measurably fails (missed deadlines despite intake discipline).

## What ships (v1 scope)

All of it lives in this repo and reaches machines via git + managed settings.

### 1. Rep workspace (`workspace/` in this repo)

- `bbs-rep.code-workspace` — harvested from `ca-quote-hub`'s workspace + extension picks,
  stripped of developer clutter. Folders: the synced
  `State of CA Agencies` path (documented `${env}` note — OneDrive paths vary per machine;
  the setup guide covers fixing the one folder path on first open). Settings: hide terminal
  panel by default, no format-on-save, file-viewer extensions only.
- Extension recommendations (small, curated): Claude Code, PDF viewer, Excel/CSV viewer,
  Material icons. Nothing else. No git extensions, no linters, no language servers.
- `CLAUDE.md` template for the SharePoint folder root — generated/audited with
  `/bbs-claude-md`, grounded in `ca-quote-hub`'s CLAUDE.md (bidder identity block, 5-row
  routing table, no-substitutions gate, pricing rules, duplicate-folder warning) minus
  anything cost/margin-related (customer-adjacent folder: SELL only).

### 2. `/bbs-checkup` command (in `bbs-foundations`)

One command a rep runs when anything feels wrong, and after setup. Verifies: plugins loaded
and versions current, marketplace reachable, connectors responding (BC via a read-only call,
Grainger, M365), OneDrive folder present and syncing, `CLAUDE.md` present at folder root.
Output ends with: what passed, what failed, and the exact sentence to send Parker if a step
failed. BC is verified through the **BC MCP (Custom API) connector** (the retired
`bbs-bc-mcp-proxy` is not checked); documents the known BC failure mode
(`Internal_CompanyNotFound` → restart session) if it still applies to the connector.

### 3. `REGISTRY.md` (repo root)

The living inventory: every BBS repo and asset, its status — **canon / harvested / parked /
archived** — and where its value went. Initial content is the consolidation map below.
Prevents the recurring "which of my attempts is current?" re-derivation.

### 4. Setup guide (`docs/REP-SETUP.md`)

Screenshot-oriented, one sitting, written for a non-technical rep: install VS Code, install
Claude Code, sign in with the BBS Claude account, open `bbs-rep.code-workspace`, run
`/bbs-checkup`, run `/bbs-my-voice` once, do one real task. Desktop-app section: "your
current setup keeps working; here's when you'd prefer VS Code." Includes Parker's admin
runbook: push managed settings from the admin console, verify on one machine, assign
connectors per the matrix.

### 5. Managed-settings final review

`bbs-managed-settings.json` gets a pre-push review in this session's plan: confirm the
`bbs-ops` → `bbs-website` rename is reflected everywhere, `${HOME}` expansion caveat,
Grainger key rotation prerequisite (leaked copy found on this machine 2026-09-11 in
`remote-settings.json`), and the Firecrawl key leak in Parker's `settings.local.json`
(~20 allowlist entries) — both keys rotated before any push.

### 6. Parker machine-cleanup checklist (`docs/ADMIN-CLEANUP.md`)

Executed deliberately, not in bulk: rotate the two leaked keys; rebuild
`~/.claude/settings.local.json` from scratch (116 entries, `Bash(bash *)`, auto-approved
`apply_migration`/`execute_sql`/`graphql_mutation` all contradict doctrine); prune
marketplaces from 11 to the vetted few; bucket global skills (BBS skills already in
marketplace → pointers; dev skills stay for Parker; dead weight deleted); remove the
caveman statusline from any config a rep could inherit; delete the OneDrive
`claude-inside-sales-skills/` folder (the original drift source).

## External tools ruling

- **Adopt: Power Automate intake flow** (already licensed, in-tenant). Email to quotes@ /
  CA-agency pattern → attachments saved to `State of CA Agencies/_inbox/<sender>-<date>/` →
  Teams notification. Removes the one manual step the M365 MCP cannot do (binary attachment
  download) and the most error-prone human step (mis-filing). Built by Parker in the portal;
  documented in the setup guide as an admin task.
- **Later: SignNow routing** for compliance-packet signatures (split authority:
  Griffin/Jackson/Parker) — v1.1, connector already on the account.
- **Later: nightly audit run** — scheduled Claude session reads `quote-log.md` files, posts
  one Teams digest (missing due dates, stale quotes, duplicate buyer folders).
- **Excluded consciously:** M365 Copilot (splits the AI habit; the moat is the Claude
  doctrine/skill layer), Copilot Studio (already shelved by bbs-rfq-automation), Zapier/n8n
  (Power Automate is the one glue tool), RAG platforms (SharePoint + canonical-facts covers
  a 9-person company), additional community marketplaces (supply-chain surface on rep
  machines).

## How it stays consistent (the keeping system)

1. **One distribution channel** — managed settings from the admin console; marketplace
   auto-update for content. No hand-copied anything.
2. **REGISTRY.md** — every asset has exactly one status and one home.
3. **Single-source rule** — a skill lives in one canonical place; every other location is a
   3-line pointer (the HANDOFF task-20 pattern, actually executed this time).
4. **Recorded verification** — `/bbs-checkup` on machines; acceptance results committed as
   dated files in `docs/acceptance/`, never left in anyone's head. The v1 acceptance gate:
   **a rep who is not Parker opens the workspace, runs `/bbs-checkup` clean, logs one real
   RFQ with `/ca-rfq-log`, and produces a quote packet with `/ca-rfq-quote` — unaided.**
   Result recorded pass/fail with date and rep initials.

## Folder-tree landmines (from `docs/assessments/2026-09-11-folder-migration-debrief.md`)

The migration to `All RFQ's by Agency/` happened Aug 11–27 on another machine; the debrief
reconstructs the convention and nine live landmines. Design consequences:

- The desk-root `CLAUDE.md` template must carry the landmines verbatim (duplicate buyer
  folders are the most expensive intake error; the CDCR "copy" trees; the live
  `CalTrans` / `Cal Trans (ALL)` duplicate pair; **folder-name typos are load-bearing** —
  account numbers ride on names, never rename; buyer notes override folder-name accounts).
- `/bbs-checkup` (or the nightly audit) detects duplicate agency/buyer folders — the
  `CalTrans` pair is the ready-made test case.
- **Open ruling needed:** deal-folder naming — the skill says item-first
  (`metal detectors naspo 8.27.26`), reps actually use date-first
  (`MM.DD - desc - buyer`). Pick one (recommend ruling in favor of observed rep behavior)
  and align the skill; a convention nobody follows is worse than none.
- `agency-tree.md` (8/27) supersedes `document-store-map.md` (8/11, pre-migration): the
  harvest target changes to agency-tree.md; the vault map gets archived, not promoted.

## The customer-desk pattern (generalization)

The SharePoint backbone — segment folder tree + root `CLAUDE.md` + intake convention +
per-buyer `quote-log.md` — is not a CA-state one-off. It is the **customer-desk pattern**,
and the State of CA Agencies desk is its first instance. Other segments (federal primes,
local fire/LE, higher-ed) get stamped from the same template: create the folder tree,
generate the root `CLAUDE.md` with `/bbs-claude-md`, adapt the intake skill's agency
registry. The rep workspace template must therefore treat the CA desk as *an instance*,
not hard-code it: the workspace file points at `Customers/` with the CA desk as the
default folder, and the folder-root CLAUDE.md template lives in `bbs-foundations` as a
reusable reference, instantiated per desk.

**SharePoint is the starting substrate, not the destination.** The durable assets are the
*conventions* — intake discipline, run records (`RFQ.md`, `quote-log.md`), the registry,
the desk CLAUDE.md — not the storage they sit on. Skills reference conventions and relative
desk paths, never absolute SharePoint paths, so the substrate can evolve (e.g., reviving
the parked Supabase `rep_cockpit` as the tracker once folder tracking shows its limits)
without retraining reps or rewriting skills. Phase-one success includes *learning what to
measure*: `/bbs-checkup` and the nightly audit are also instruments for discovering where
folders stop being enough.

## Rep-deployable agency tenants (bbs-customer-bots)

Twelve agency gear-assistant tenants exist (`cdcr` reference implementation; `<id>.blackboxsafety.com`).
The `new-agency-tenant` skill is the playbook, but today it is admin-grade: it edits code
(`src/tenants/<id>.js`), requires SCPRS/BC/Grainger curation, and ends in a Vercel deploy —
which conflicts with the rep permission profile (read-only ops, deploys gated).

**Ruling for this rollout:** tier it rather than fork it.
- **v1:** reps get tenant *awareness* — `/bbs-checkup`-style visibility of which tenants
  exist and a documented request path ("ask for a tenant" = drop agency name + buying
  context into a folder; Parker runs the skill).
- **v1.1:** the skill gains a **rep mode**: the rep's Claude session does the curation
  (facility roster from BC, buying history from SCPRS, account discovery via Grainger MCP)
  and produces the tenant file + a PR with a preview URL; Parker's merge is the deploy.
  This honors plan → approve → execute: rep does 95% of the work, the one irreversible
  step stays gated. The skill's own silent-failure checklist (registry checks, live-site
  console read) becomes the PR's acceptance section.

## Marketing desk (second instance of the pattern)

The marketing effort is not a named agent — it is an early second instance of the
customer-desk pattern: a SharePoint folder ("BBS Marketing") holding consistent reference
material, plus a skill built for Joey that works. That is evidence the pattern transfers
beyond quoting. Design intent, in order:
1. **Now:** inventory what's in the BBS Marketing folder and where Joey's skill lives
   (likely hand-copied — the same drift risk the marketplace exists to fix).
2. **v1.1:** give the marketing folder a root `CLAUDE.md` (same forge), move Joey's skill
   into the marketplace as the seed of a **`bbs-marketing` plugin**, and migrate
   `grainger-promo-page` into it from `bbs-sales` (it is outbound campaign work).
3. Reps "creating opps" = the promo-page + SCPRS segmentation workflow already in the
   marketplace, surfaced through the marketing desk.
