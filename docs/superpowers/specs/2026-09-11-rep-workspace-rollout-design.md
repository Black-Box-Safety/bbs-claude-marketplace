# Rep workspace rollout — design

**Date:** 2026-09-11 · **Owner:** Parker Marshall · **Status:** v1 built (this repo, 2026-09-13) — deployment checklist: docs/ADMIN-RUNBOOK.md §0–§3

## The business problem (why any of this matters)

Reps cannot drive new sales because stale processes trap the team in reactive work:
inbound RFQs, customer service, documentation, email management. The low-level load
consumes the capacity that should extend existing customers and open truly new business.

Compounding it: **there is no infrastructure for tracking performance or quoting fast from
history.** What BBS bid a customer before — items, prices, outcome — lives in individual
recall, not in queryable records. Every quote starts from scratch; pricing knowledge cannot
be learned from, verified, or handed to a new rep. The team trusts memory where it should
be reading documented success.

Everything in this design is therefore judged against two outcomes, in order:

1. **Reclaim capacity** — automate the labor in the inbound/service load (this design's v1).
2. **Convert that capacity into growth motion** — reclaimed hours must be deliberately
   redirected into outbound and expansion work, with vehicles and measures, or they will
   silently backfill into more inbound. Efficiency alone does not create a single new
   customer. See "From reactive to generative" below.

## The tooling problem (what blocks outcome 1)

Black Box Safety has designed rep-facing AI infrastructure five times (bbs-ops/bbs-website,
bbs-sales, bbs-sales-vault, ca-quote-hub, bbs-rfq-automation) and deployed none of it to the
people it was built for. Rep machines run Claude Code in the Desktop app with hand-copied,
drifted skills that trace back to a OneDrive folder from June 2026. The managed-settings
design (2026-09-02) was finished and never pushed. The bbs-ops acceptance test was never
recorded. Two different `ca-rfq-intake` skills exist and collide silently.

The bottleneck is not design quality — it is that every rollout stalled at the deployment
step, and nothing enforces consistency once a machine is set up. Parker is the only
technical person (self-taught), so the system must be manageable by one busy non-engineer:
central control, no per-machine state, boring failure modes.

Meanwhile the sales team is trained, willing, and seeing ROI. They already: save inbound
RFQs into folders, point a Claude Code session (Desktop app) at the folder, and run skills.
The new SharePoint home base is being established at
`Black Box Safety - MASTER/Customers/State of CA Agencies/` (OneDrive-synced to each PC).

## The decision

**Marketplace-first thin client.** A rep machine has exactly four things, none hand-configured:

1. **Org managed settings** pushed from the Claude admin console (Team/Enterprise) —
   plugins, conservative permissions, company memory (`claudeMd`), announcements.
   Source of truth: `plugins/bbs-foundations/docs/bbs-managed-settings.json` in this repo.
   Local edits are overwritten on refresh; drift becomes structurally impossible.
2. **The marketplace plugins** (`bbs-foundations`, `bbs-sales`, `bbs-website` advisory,
   pinned externals) — ride in via managed settings, auto-update through git.
3. **The OneDrive-synced SharePoint folder** as the working home base, opened through a
   versioned `bbs-rep.code-workspace`, with a `CLAUDE.md` at the folder root generated by
   `bbs-claude-md-forge`.
4. **claude.ai connectors** assigned per role (BC read-only + M365 + Grainger for everyone;
   admin connectors stay with Parker/Griffin) — managed in claude.ai Settings, per the
   matrix in `MANAGED-SETTINGS.md`.

**Surface: VS Code standard, Desktop app unchanged.** Reps already run Claude Code inside
the Desktop app; that keeps working untouched and is the documented escape hatch. VS Code
is the encouraged standard because quote work is multi-document work (worksheet + attachments

+ precedent side by side, file tree visible next to Claude). Same Claude Code underneath —
  same skills, sessions, connectors — so adopting VS Code is a window change, not a retraining.
  The rep pitch, verbatim: *"Everything you do today keeps working. VS Code shows you what
  Claude is reading."*

### Alternatives rejected

- **claude.ai web only** — no local folder access; fails the folder workflow.
- **Desktop app as the standard** — already works, but no file tree / side-by-side documents;
  kept as the fallback rather than the destination.
- **Power Platform rep app (bbs-rfq-automation)** — live parallel build targeting a Dataverse
  model-driven app. Formally **parked** as a rep destination: it has been blocked for weeks on
  enterprise-IT portal work only Parker can do, which is exactly the manageability failure
  this design avoids. Its ruled invariants (humans send quotes; sell = Grainger cost
  untransformed; no default-account fallback; nothing silently dropped) are already doctrine
  and are retained.
- **Supabase rep_cockpit (ca-quote-hub) as the home base** — parked. Folder-based tracking via
  `ca-rfq-intake` + `quote-log.md` covers v1; revisit the database pipeline only if folder
  tracking measurably fails (missed deadlines despite intake discipline).

## How it stays consistent (the keeping system)

1. **One distribution channel** — managed settings from the admin console; marketplace
   auto-update for content. No hand-copied anything.
2. **REGISTRY.md** — every asset has exactly one status and one home.
3. **Single-source rule** — a skill lives in one canonical place; every other location is a
   3-line pointer (the HANDOFF task-20 pattern, actually executed this time).
4. **Recorded verification** — `/bbs-checkup` on machines; acceptance results committed as
   dated files in `docs/acceptance/`, never left in anyone's head. The v1 acceptance gate:
   **a rep who is not Parker opens the workspace, runs `/bbs-checkup` clean, logs one real
   RFQ with `/ca-rfq-log`, and produces a quote packet with `/ca-rfq-quote` — unaided.**
   Result recorded pass/fail with date and rep initials.

## The customer-desk pattern (generalization)

The SharePoint backbone — segment folder tree + root `CLAUDE.md` + intake convention +
per-buyer `quote-log.md` — is not a CA-state one-off. It is the **customer-desk pattern**,
and the State of CA Agencies desk is its first instance. Other segments (federal primes,
local fire/LE, higher-ed) get stamped from the same template: create the folder tree,
generate the root `CLAUDE.md` with `/bbs-claude-md`, adapt the intake skill's agency
registry. The rep workspace template must therefore treat the CA desk as *an instance*,
not hard-code it: the workspace file points at `Customers/` with the CA desk as the
default folder, and the folder-root CLAUDE.md template lives in `bbs-foundations` as a
reusable reference, instantiated per desk.

**SharePoint is the starting substrate, not the destination.** The durable assets are the
*conventions* — intake discipline, run records (`RFQ.md`, `quote-log.md`), the registry,
the desk CLAUDE.md — not the storage they sit on. Skills reference conventions and relative
desk paths, never absolute SharePoint paths, so the substrate can evolve (e.g., reviving
the parked Supabase `rep_cockpit` as the tracker once folder tracking shows its limits)
without retraining reps or rewriting skills. Phase-one success includes *learning what to
measure*: `/bbs-checkup` and the nightly audit are also instruments for discovering where
folders stop being enough.

## Rep-deployable agency tenants (bbs-customer-bots)

Twelve agency gear-assistant tenants exist (`cdcr` reference implementation; `<id>.blackboxsafety.com`).

  This honors plan → approve → execute: rep does 95% of the work, the one irreversible
  step stays gated. The skill's own silent-failure checklist (registry checks, live-site
  console read) becomes the PR's acceptance section.

## How it all fits together (the system in one view)

Visual companion: the "BBS AI Operating System" artifact (published 2026-09-11).

**The value chain (figurative stack)** — each layer consumes the one beneath it, and
nothing skips a layer:

```text
CUSTOMER        CA agency buyer: compliant, priced, DVBE-credited answer, fast
   ▲  the answer
SURFACES        quote packet + forms · storefront · agency tenants · promo pages · rep email
   ▲  drafts — a human reviews every number, then sends
REP DESK        Claude session on the SharePoint desk (VS Code / Desktop app)
                inbound: intake → precedent → price → packet → record → human sends
                outbound: SCPRS segments → promo / winback / follow-up (1 motion/rep/week)
   ▲  skills load the BBS way of each job
KNOWLEDGE       marketplace plugins (foundations · sales · website) + desk CLAUDE.md
   ▲  facts read live from systems of record, never copied into prompts
DATA            BC (money) · Grainger MCP (price) · SCPRS (market) · SharePoint (docs)
                · bbs-suppliers (leverage)        ⟂ GOVERNANCE (settings·hooks·checkup·
                                                     flags·metrics·registry) holds all layers
```

**The literal architecture** — the rep's Claude session is the hub. Two control channels
flow in (admin console → managed settings, hourly; GitHub marketplace → skills,
auto-update on push). Data connectors flow in read-only, one source per fact. Output lands
only as reviewable files in the OneDrive-synced desk; the only writes to the outside world
(send, submit, SQ entry in BC) pass through a human hand, hook-enforced, with the SQ read
back and verified. Consequence: **no rep-machine state matters** — any machine rebuilds in
minutes from console + git + OneDrive, so drift is structurally impossible and support is
"restart and re-sync."

**The flywheel (why it compounds, not just accelerates):** inbound handled fast → the
record grows (BC quote, quote-log, outcome) → the next quote is faster and smarter
(precedent in seconds) → hours freed → outbound motion (SCPRS-aimed) → new business →
more inbound. Inner loop: flags → skill fixes, golden set guards changes, metrics steer
investment. The outer ring is the revenue engine; the inner loop is the quality engine.
A team with only the outer ring gets faster; with both, it gets better.

## Competitive reality (ruling, 2026-09-11)

**NASPO quotes are uncompetitive on price.** The schedule is the convenience/contract-
vehicle lane, not the growth lane. Design consequences:

- **Automate NASPO inbound to near-zero rep effort** — it's volume to be handled, not
  business to be fought for. The naspo-quote pipeline's job is speed and compliance, and
  minimal rep minutes.
- **The competitive weapons get the rep time:** the SB/DVBE competitive lane (5% SB
  preference + DVBE incentive apply there — SCM 1204/1202, competitive solicitations
  only) and `bbs-sourcing`'s vendor-negotiated pricing, where BBS can actually beat a
  price rather than match a schedule. Supplier leverage context comes from
  `bbs-suppliers` (see data plane).
- Win-rate measurement (precedent engine) should segment by lane — NASPO vs competitive —
  or the blended number hides exactly the insight this ruling encodes.

## The precedent engine (documented success replaces recall)

The design's answer to "we trust recall": before any price goes out, the rep's Claude
session checks the record, and after any quote goes out, the record grows. Four layers,
all already designed — this section names them as one system and makes "check precedent
first" a required step, not a habit:

1. **BC sales quotes** (v1.1 loop) — the structured layer: what was quoted to which
   customer, at what price, and (with sentDate/acceptedDate hygiene) whether it won.
   `bc_get_sales_document` / `bc_customer_snapshot` answer "what did we bid CMC in March?"
   in one query. This is the layer that turns quoting into learning: win rate per agency,
   price points that convert, items that repeat.
2. **The desk folder tree** — the document layer: per-buyer `quote-log.md` (Date / Item /
   Quote# / Vehicle / Value / **Outcome**) plus the `FILLED/` packets. The intake skill's
   "search by buyer AND item before creating anything" rule is the retrieval discipline;
   duplicate folders are precedent-destroyers (see landmines).
3. **Mined form precedents** — `naspo-quote`'s references were built from ~440 historical
   PDFs; every form default is the documented majority answer, not a guess. This layer
   already exists and proves the model works.
4. **The flag log + golden set** — the learning layer: what went wrong feeds skill fixes;
   what was verified correct becomes regression cases.

**Skill change (v1.1, rides with the BC quote step):** `naspo-quote` opens with a
precedent check — prior quotes to this buyer (BC + quote-log), prior wins on these items —
and cites what it found in the cover summary ("last quoted 3M 8511 to CMC 3/2026 at $X,
won"). The rep sees the history without asking anyone; the Outcome column stops being
optional. **Success test:** a rep who has never worked an account can answer "what did we
bid them before and did we win?" in under a minute, from records.

## From reactive to generative (the conversion mechanism)

The rollout fails in the way that matters if quote turnaround drops 40% and outbound
activity stays at zero. Freed capacity converts only if the growth motions are named,
tooled, and measured:

**The growth vehicles (all already exist as tools — none are new builds):**

- **`grainger-promo-page` + SCPRS segmentation** — the flagship outbound motion: turn an
  agency's existing spend into a targeted campaign page for the three buyer segments
  (buys prime direct / buys category elsewhere / BBS history but drifted). This is the
  workflow reclaimed hours should flow into first.
- **Drifted-buyer winback** — the SCPRS "has BBS history but drifted" segment is a standing
  call list; Claude drafts the re-engagement outreach in the rep's voice.
- **Stale-quote follow-up** — once quotes live in BC (v1.1 loop), "sent >14 days, no
  outcome" is a follow-up queue, not a dead file. The nightly Routine surfaces it.
- **New-desk expansion** — the customer-desk template stamped onto federal primes /
  local fire-LE is the structural version of "new business."
- **Agency tenants** — a rep-initiated tenant (v1.1 PR flow) turns one buyer's reorder
  pattern into a self-service storefront for the whole agency.

**The operating change:** the weekly rhythm gains one explicit expectation — reclaimed
time has a default destination. Concretely: each rep runs one outbound motion per week
(a promo page, a winback batch, or a follow-up sweep), tracked in the same weekly log as
the inbound metrics. Parker's monthly review reads both halves together.

**Measurement gains a second half.** The four inbound metrics (quotes/rep/week,
turnaround, win rate, adoption) get four outbound counterparts in `docs/MEASUREMENT.md`:
outbound touches/week, promo pages shipped, winback conversations started, reactivated or
net-new buyers per month (from BC — a first order from a customer number with no activity
in 12 months). Leading indicators are the touches; the lagging proof is net-new buyers.
